# Manual Deployment — LKE with Karpenter

This runbook walks through the Kubernetes-side setup after `./start.sh` has provisioned the LKE Standard cluster:

1. Install the Linode Cloud Firewall Controller.
2. Install the Linode Karpenter provider.
3. Create a default NodePool.
4. Simulate scale-up and scale-down with the `inflate` workload.
5. Verify the correct logs.

> **Alpha software warning**
> The [Linode Karpenter provider](https://github.com/linode/karpenter-provider-linode) is currently **alpha** and under active development. Do not use it for production workloads. APIs, CRDs, and behaviour may change.

---

## Prerequisites

Run all commands from the `lke_with_karpenter/` directory and set the kubeconfig generated by `start.sh`:

```bash
export KUBECONFIG="$PWD/kubeconfig.yaml"
export LINODE_TOKEN="<your-linode-api-token>"
```

Tools assumed: `kubectl`, `helm`, `tofu`.

Verify the cluster is ready:

```bash
kubectl get nodes -o wide
# Expected: 3 Ready nodes of type g6-standard-2 in gb-lon
```

---

## Step 1 — Install the Linode Cloud Firewall Controller

The controller creates and maintains a Linode Cloud Firewall for every node in the cluster, providing a default secure ruleset for LKE.

### 1.1 Add the Helm repository

```bash
helm repo add linode-cfw https://linode.github.io/cloud-firewall-controller
helm repo update linode-cfw
```

### 1.2 Install the CRD

```bash
helm upgrade --install cloud-firewall-crd \
  linode-cfw/cloud-firewall-crd \
  --version 0.2.0 \
  --namespace kube-system \
  --wait --timeout 2m
```

Wait for the CRD to be established:

```bash
kubectl wait --for condition=established --timeout=60s \
  crd/cloudfirewalls.networking.linode.com
```

### 1.3 Install the controller

```bash
helm upgrade --install cloud-firewall \
  linode-cfw/cloud-firewall-controller \
  --version 0.2.1 \
  --namespace kube-system \
  -f configs/cloud-firewall/values.yaml \
  --wait --timeout 5m
```

### 1.4 Verify

```bash
kubectl -n kube-system get pods -l app.kubernetes.io/name=cloud-firewall-controller

# Expected output:
# NAME                                  READY   STATUS    RESTARTS   AGE
# cloud-firewall-controller-...         1/1     Running   0          Xm
```

A Cloud Firewall named `lke-<cluster-id>` is created in your Linode account. It may take 1–2 minutes to appear after the pod starts.

## Step 2 — Install the Linode Karpenter Provider

Karpenter is installed from the chart source in the provider repository. You can either clone the repository or reference the chart directly via the GitHub URL.

### 2.1 Set cluster name

```bash
export CLUSTER_NAME="$(tofu output -raw cluster_label)"
echo "Cluster name: ${CLUSTER_NAME}"
```

### 2.2 Clone the provider chart (recommended for this PoC)

```bash
# Outside this project, or in a temporary directory
git clone --depth 1 https://github.com/linode/karpenter-provider-linode.git /tmp/karpenter-provider-linode
```

### 2.3 Install the Karpenter CRD

```bash
helm upgrade --install karpenter-crd \
  /tmp/karpenter-provider-linode/charts/karpenter-crd \
  --namespace kube-system \
  --create-namespace \
  --wait --timeout 2m
```

### 2.4 Install the Karpenter controller

```bash
helm upgrade --install karpenter \
  /tmp/karpenter-provider-linode/charts/karpenter \
  --namespace kube-system \
  --create-namespace \
  --set settings.clusterName="${CLUSTER_NAME}" \
  --set apiToken="${LINODE_TOKEN}" \
  --set settings.mode=lke \
  -f configs/karpenter/values.yaml \
  --wait --timeout 5m
```

> **Security note for GitOps**
> Passing `apiToken` via `--set` is acceptable for a manual PoC. For GitOps, create a Kubernetes Secret with keys `LINODE_TOKEN`, `LINODE_URL`, `LINODE_API_VERSION` and use `--set credentialsSecretRef=<secret-name>` instead.
>
> Even for this PoC: `helm get values karpenter -n kube-system` will print the
> token in plaintext, and it remains recoverable from **every prior Helm
> revision**, not just the current one (`helm history` + `helm get values
> karpenter --revision <n>`). Treat any token passed this way as sensitive —
> avoid running that command on a shared screen, and rotate the token in the
> Linode Cloud Manager once you're done with the demo.

### 2.5 Verify

```bash
kubectl -n kube-system get pods -l app.kubernetes.io/name=karpenter

# Expected: 2 Running pods (default replica count)
```

## Step 3 — Create a NodePool

Apply the default NodePool supplied in this repo. It limits total Karpenter-managed capacity to 32 CPU cores as a PoC guardrail.

```bash
kubectl apply -f configs/karpenter/nodepool.yaml
```

Verify:

```bash
kubectl get nodepools
kubectl get linodenodeclasses

# Expected:
# NAME      NODECLASS   ...
# default   default     ...
```

Karpenter is now watching for unschedulable pods and will create LKE NodePools sized to fit them.

> **Note on `consolidationPolicy`**  
> Current Karpenter v1 CRDs only accept `WhenEmpty` or `WhenEmptyOrUnderutilized`.  
> The legacy value `WhenUnderutilized` (used in older provider examples) is rejected by the API server. This demo uses `WhenEmptyOrUnderutilized` so Karpenter removes or replaces nodes that are empty or underutilized.

## Step 4 — Simulate Scale Up

Deploy the `inflate` pause workload from the upstream provider README and scale it out. Each replica requests 1 CPU, which cannot fit on the small `g6-standard-2` baseline nodes once the cluster is modestly utilised, triggering Karpenter to add capacity.

### 4.1 Deploy `inflate`

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: inflate
spec:
  replicas: 0
  selector:
    matchLabels:
      app: inflate
  template:
    metadata:
      labels:
        app: inflate
    spec:
      terminationGracePeriodSeconds: 0
      securityContext:
        runAsUser: 1000
        runAsGroup: 3000
        fsGroup: 2000
      containers:
        - name: inflate
          image: public.ecr.aws/eks-distro/kubernetes/pause:3.7
          resources:
            requests:
              cpu: 1
          securityContext:
            allowPrivilegeEscalation: false
EOF
```

### 4.2 Scale up

To reliably see a clean first-attempt scale-up in a demo, scale gradually
instead of jumping straight to 5 replicas — see the callout below for why.

```bash
kubectl scale deployment inflate --replicas 4
# wait for the new node to be Ready, then:
kubectl scale deployment inflate --replicas 5
```

Jumping directly to `--replicas 5` also works, but is more likely to trigger
the known stuck-pool issue described below, since it requires 2 NodeClaims
(and therefore 2 concurrent LKE pool-create calls) instead of 1.

### 4.3 Watch the cluster react

In one terminal, tail the Karpenter controller logs:

```bash
kubectl logs -f -n kube-system -l app.kubernetes.io/name=karpenter -c controller
```

In another terminal, watch nodes and pods:

```bash
watch -n 2 'kubectl get nodes -o wide && echo "---" && kubectl get pods -o wide'
```

What to look for:

- `inflate-*` pods are `Pending`.
- Karpenter logs show `created nodeclaim` / `launched nodeclaim`.
- New nodes appear in `kubectl get nodes`, usually within 1–2 minutes.
- Pods move to `Running` once nodes join.

> **Known issue: occasional stuck NodePool, strongly correlated with
> concurrent pool creation.**
> The Linode LKE backend occasionally fails to assign an `instance_id` to a
> newly created NodePool. Root-caused (see `TROUBLESHOOTING_STATUS.md`) to
> **concurrent pool-create requests against the same cluster** — reproduced
> directly against the Linode API with no Karpenter involved: 2 pool-create
> requests fired at the same instant reliably got stuck; sequential requests
> did not, in every trial run. When 2+ pods need capacity at the same moment,
> Karpenter launches one `Create()` call per `NodeClaim` concurrently, which
> triggers this. Scaling by one pod's worth of capacity at a time (as in
> 4.2 above) avoids it in practice.
>
> When it does happen, Karpenter waits out `settings.lkeCreateDeadline`
> (5 minutes in this demo), deletes the `NodeClaim`, and automatically
> retries — the retry has consistently succeeded in testing. Worst case, a
> pod can take **up to ~10 minutes** to schedule instead of ~1–2 minutes.
> This is a backend/provider issue, not a misconfiguration in this repo —
> there is no `NodePool`/`NodeClass`/Helm value that prevents it (confirmed
> by reviewing `pkg/providers/lke/lke.go` in the provider source).
>
> **Side effect:** when this happens, Karpenter deletes the Kubernetes
> `NodeClaim` but does **not** delete the underlying LKE NodePool, leaving it
> orphaned forever at `instance_id: null`. Run `./scripts/gc-orphaned-pools.sh
> <cluster-id>` after a demo session to detect and clean these up (they cost
> nothing while `instance_id` is null, since no Linode instance was ever
> created, but they clutter `linode-cli lke pools-list` output).

## Step 5 — Simulate Scale Down

### 5.1 Delete the workload

```bash
kubectl delete deployment inflate
```

### 5.2 Watch consolidation

Tail the logs again:

```bash
kubectl logs -f -n kube-system -l app.kubernetes.io/name=karpenter -c controller
```

Watch nodes:

```bash
watch -n 2 'kubectl get nodes -o wide'
```

What to look for:

- Karpenter logs show `disrupted nodeclaim` / `deleted nodeclaim`.
- Empty Karpenter-provisioned nodes are cordoned, drained, and removed.
- The cluster returns to the original 3 baseline nodes.

> **Note:** consolidation does not remove the manually provisioned baseline pool nodes created by Terraform. It only removes Karpenter-managed NodeClaims.

## Step 6 — Logs to Check

| Component | Command | What to look for |
|-----------|---------|------------------|
| Karpenter controller | `kubectl logs -f -n kube-system -l app.kubernetes.io/name=karpenter -c controller` | `created nodeclaim`, `launched nodeclaim`, `registered nodeclaim`, `disrupted nodeclaim`, registration errors, duplicate NodeClaims |
| Cloud Firewall Controller | `kubectl logs -f -n kube-system -l app.kubernetes.io/name=cloud-firewall-controller` | Reconciliation of firewall devices, rule application, errors adding/removing nodes |
| Nodes | `kubectl get nodes -o wide` | New nodes joining, taints removed, Ready state |
| Pods | `kubectl get pods -o wide -w` | Pods transitioning from Pending to Running |
| NodeClaims | `kubectl get nodeclaims` | Lifecycle of Karpenter-managed capacity |
| NodePools | `kubectl get nodepools` | Resource usage against limits |

> **Known LKE cluster-side issue: konnectivity 500 breaks `kubectl logs` /
> `stern`.** Observed in this demo on 2026-07-10. Symptom: every `kubectl
> logs` / `stern` call against any pod returns
> `proxy error from konnectivity-server.kube-system-<cluster>.svc:8090
> while dialing <node-ip>:10250, code 500: 500 Internal Server Error`.
> The konnectivity **server** (LKE-managed, in the control plane) is
> returning 500 when the apiserver asks it to dial a node's kubelet on
> port `10250`; the konnectivity **agents** in the worker pool are healthy.
> Karpenter itself is **not** affected — it reports progress via NodeClaim
> status conditions and Kubernetes events, which go through the apiserver's
> normal REST API, not konnectivity. When this happens, fall back to:
>
> ```bash
> kubectl get nodeclaim -o wide
> kubectl describe nodeclaim <name>
> kubectl get events -A --sort-by=.lastTimestamp | tail -30
> ```
>
> To read controller logs without konnectivity, use Linode LISH/SSH on the
> worker that hosts the leader pod (find it via
> `kubectl get events -A | grep LeaderElection`) and run
> `sudo crictl logs <container-id>`. Full diagnosis and escalation
> template: `TROUBLESHOOTING_STATUS.md` § "2026-07-10 (session 2)
> follow-up: konnectivity 500 breaks `kubectl logs`/`stern`".

## Cleanup

First, check for and remove any LKE NodePools orphaned by the stuck-pool
issue described in Step 4 (`./shutdown.sh` only destroys resources tracked in
Terraform state, so orphaned pools created directly via the Linode API by
Karpenter will **not** be cleaned up by it):

```bash
./scripts/gc-orphaned-pools.sh "$(tofu output -raw cluster_id)"
```

Then run the demo teardown script from the project root:

```bash
./shutdown.sh
```

This prompts for confirmation before destroying the LKE cluster and removing `kubeconfig.yaml`.

If you want to remove only the Kubernetes components manually:

```bash
kubectl delete -f configs/karpenter/nodepool.yaml
helm uninstall karpenter -n kube-system
helm uninstall karpenter-crd -n kube-system
helm uninstall cloud-firewall -n kube-system
helm uninstall cloud-firewall-crd -n kube-system
```
